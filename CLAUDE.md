# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

LIMPIEZIOT — PWA for monitoring and managing a network of ESP32-based vending machines that dispense liquid cleaning products (tanks, sales, cash balance, physical security alerts). React 18 + Vite 6 + Tailwind CSS + Supabase, deployed to Cloudflare Pages (production: https://sw-pwa-vm-management.pages.dev/). UI text, comments, and commit context are in Spanish.

## Commands

```bash
npm run dev       # Vite dev server at http://localhost:5173
npm run build     # Production build to dist/
npm run preview   # Serve the production build locally
```

There are no tests. `npm run lint` is defined in package.json but ESLint is not installed, so it fails — don't rely on it.

`node scripts/build-icons.mjs` regenerates `public/` icons from `src/assets/logo-source.png` (requires the `sharp` devDependency; not part of the production bundle).

## Environment / Demo Mode

Supabase credentials come from `.env` (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`; template in `.env.example`). **Only variables prefixed `VITE_` reach the browser** — the unprefixed `SUPABASE_SERVICE_ROLE_KEY` in `.env` is for the webhook and must never gain a `VITE_` prefix.

The central switch is `isDemoActive()` in `src/lib/demoMode.js`. Demo Mode is active when credentials are missing (`isSupabaseConfigured` is false) **or** when the visitor entered the demo from the landing/login shortcuts (`switchDemoRole`), persisted in `sessionStorage`. Either way the app runs against `src/mock/sampleData.js` and **no request reaches the database**. `IS_DEMO` exported from `dataAccess.js` is that function - call it, `IS_DEMO()`, never treat it as a constant (a bare `if (IS_DEMO)` is always truthy). React components read `isDemo` from `useAuth()` so state and data layer cannot diverge: previously the demo shortcut only set React state, so in production it created an unauthenticated session querying the real database.

**Demo Mode is entered ONLY by missing configuration — never by a failed query.** All services go through `query()` / `mutate()` in `src/lib/dataAccess.js`, which log the PostgREST `code`/`message`/`hint` and throw a `ServiceError`. Pages render `<ErrorState>`.

> This replaced the previous `if (!error) return data;` pattern, where a schema mismatch silently returned mock data and the UI displayed fabricated figures as if they were real. **Do not reintroduce it.** When adding a service, use `query()`/`mutate()` and keep the demo branch's filtering semantics equivalent to the Supabase branch.

`src/mock/sampleData.js` mirrors the real schema, including the edge cases of the sale-income link: mixed payment, two incomes of the same type, failed sale with no income, legacy `tx_id: null`, orphan income, and success-without-income.

## Architecture

- **Routing** (`src/App.jsx`): public routes `/landing` and `/login`; everything else is nested under a `ProtectedRoute` + `Layout` (Sidebar/Navbar shell rendering pages via Outlet). Unauthenticated users are redirected to `/landing`. SPA routing on Cloudflare Pages depends on `public/_redirects` (`/* /index.html 200`).
- **Auth & roles** (`src/context/AuthContext.jsx`): wraps Supabase Auth (email/password + Google OAuth) with a demo fallback (`loginWithEmail` matches against `sampleProfiles`; `switchDemoRole` swaps demo roles). After login it fetches the user's row from the `profiles` table. Roles are `admin | technician | viewer`; consume them via `useAuth()`'s `role`, `isAdmin`, `isTechnician` (technician check includes admin), and `isDemo`.
- **Multi-tenant scoping**: `profiles.assigned_machine_ids` (TEXT[]) is the *only* thing that decides which machines a user sees, **with no exception for admins**. `getMachines(ids)` returns `[]` when the array is empty or missing — no assignment means no machines — and `applyCommonFilters` turns `machineIds: []` into `in.()`, which matches zero rows. Role decides *what you can do*; `assigned_machine_ids` decides *on which machines*. Assignments are made **by SQL only** (see `.doc/RLS_MULTITENANT.sql`); there is no assignment UI. Machines are likewise created **only in the database**, once the hardware is built and tested, together with their 8 `machine_tanks` rows and their `machine_status` — the PWA has no create-machine path.
- **Data layer** (`src/services/*.js`): plain async functions per domain; no state library. Every read takes an optional `filters` object (`machineIds`, `productId`, `from`, `to`, ...) applied server-side via `src/services/_filters.js`. Supabase joins return related rows as arrays, so services normalize `machine_status` from array to single object.
- **Sales ↔ incomes**: there is **no FK** between `sales` and `sale_incomes`, so PostgREST cannot join them. `getSalesWithPayments()` runs two queries and merges on `(machine_id, tx_id)` using `src/lib/salesLink.js`. The relation is **1:N** (mixed payment), `tx_id` is nullable (pre-fw-2.1.0 rows), and a `status='fail'` sale never has an income. Never pair by `created_at` proximity — the webhook processes both messages concurrently.
- **Precios y niveles mínimos de tanques**: se editan **sólo** desde el botón superior «Precios y niveles mínimos» de `MachineDetail` (`TankSettingsEditor` → `saveMachineTankSettings`), nunca por tanque suelto: el downlink `{device_id}/config/prices` lleva siempre los 8 tanques y el firmware no admite actualización parcial. Las reglas de `price_per_liter` y `low_threshold_liters` viven en **`validateTankRow()`** (`machineService.js`), una sola función que comparten el editor y el guardado — duplicarlas dejaría que el editor aceptara lo que el guardado rechaza. Son cuatro, y ninguna es cosmética: **formato llano** (`^\d+(\.\d+)?$`, lo único que entiende el parser manual del ESP32; `JSON.stringify` emite exponencial por debajo de 1e-6), **> 0** (el firmware descarta en silencio un `<= 0` y aun así responde `ack "stored"`; `mqtt-publisher` responde 400), **máximo 2 decimales en el precio y 3 en el nivel** (`NUMERIC(10,2)` y `NUMERIC(8,3)` redondean en silencio, pero el downlink se publica desde el formulario, no desde lo guardado: un 15.005 dejaría la base en 15.01 y la máquina en 15.005) y **< 1e6** (cota que exige `mqtt-publisher`). En los cuatro casos el fallo es el mismo: la base y la máquina discrepan y la máquina queda «Pendiente de sincronizar» de forma permanente. Desde 2026-08-28 la base respalda el `> 0` con CHECKs propios (`.doc/CHECKS_MACHINE_TANKS.sql`); el CHECK de fábrica era `>= 0` y `low_threshold_liters` no tenía ninguno. **No relajar ninguna de las cuatro.**
- **La PWA no escribe medidas de la máquina**: el nivel de los tanques (`machine_tanks.current_liters`, `is_above_minimum`, `last_refill_at`) y las filas de `tank_operations` los publica el equipo por MQTT y los escribe el consumidor; la interfaz sólo los lee. No reintroducir un registro manual de recargas — habría dos fuentes de verdad para la misma medida. La única escritura de la PWA sobre `machine_tanks` es la configuración de precios y niveles mínimos, que es un parámetro y viaja de vuelta al equipo por downlink.
- **`available_balance` vs `stored_cash_balance`**: son dos cifras distintas de `machine_status` y confundirlas es fácil. La primera es el **saldo de la sesión en curso** (monedas insertadas y no gastadas; baja al concretarse la venta) y se muestra como «Saldo sin reclamar» en `SecurityBadge`. La segunda es el **dinero físicamente acumulado en el monedero**: sube con cada moneda, **no** baja con la venta —el dinero ya está dentro— y sólo vuelve a 0 con el corte de caja del menú de servicio S3.3 del equipo. Es la que la PWA llama «dinero en monedero» / «pendiente de recolectar» y la que aparece en el Dashboard, en el catálogo y en la cabecera de `MachineDetail`. Ninguna de las dos la escribe la PWA: llegan en el bloque `security` de la telemetría.
- **Role checks in the client are NOT a security boundary**: `isAdmin`, `isTechnician` and the `assigned_machine_ids` filtering in `getMachines()` / `_filters.js` decide what is *rendered*, not what the database *returns* - the anon key ships in the bundle, so anyone can call PostgREST directly. The only real boundary is RLS. See `.doc/RLS_MULTITENANT.sql`: until it is applied, policies are `to authenticated using (true)` and any signed-in user can read every machine's data.
- **Writes the PWA is allowed to make**: only three, each gated in the DB by role *and* by machine — `machine_tanks` (prices/min levels), `system_alerts` (resolve/reopen), and `machines` **name + location only**, admin-only, via `updateMachineInfo()`. That last one is additionally constrained *by column*: `grant update (name, location_address) on machines to authenticated`, because RLS is row-level and cannot limit columns. **Adding another field to that update payload will fail with a permission error until the grant is widened** — column privileges are evaluated before RLS and are all-or-nothing per statement, so a single ungranted column kills the whole UPDATE with `permission denied for table machines` (42501), naming the *table*, not the column. That is exactly what `updated_at` in the payload did until 2026-08-29; it is now maintained by the `machines_set_updated_at` trigger (`.doc/RLS_MULTITENANT.sql`, PASO 4.c) instead of being sent from the client — and `device_id` must never be widened in, since it is the key the MQTT consumer joins on and changing it silently detaches the machine from its telemetry. Everything else about a machine is published by the device.
- **Design tokens**: colors are CSS variables in `src/styles/tokens.css`, exposed through `tailwind.config.js` as `rgb(var(--x) / <alpha-value>)`. `brand` and `slate` are **overridden** to read tokens, which is why the palette changed without editing ~1000 utility classes. New code should use the semantic tokens (`surface`, `line`, `content`, `accent`, `status`). To recolor the brand: the three `--brand-*` primitives plus `BRAND_HEX` in `src/theme/brand.js`, then `node scripts/build-icons.mjs`.
- **Data flow (big picture)**: ESP32 machines publish MQTT (sales, income, telemetry/security, alerts) → a backend consumer writes to Supabase tables (`machines`, `machine_status`, `machine_tanks`, `sales`, `sale_incomes`, `tank_operations`, `system_alerts`) → this PWA reads them. The PWA never talks to MQTT; it only reads/writes Supabase.
- **PWA** (`vite.config.js`): `vite-plugin-pwa` with autoUpdate; Supabase API responses are cached NetworkFirst for 24h by Workbox — stale data after connectivity loss is expected behavior, not a bug.

## Internal docs

`.doc/` is gitignored (kept out of the public repo intentionally) but present locally: `architecture_proposal.md` (frontend, incl. the RBAC matrix and what was removed from the UI), `backend_architecture_proposal.md` (MQTT consumer + table mapping, includes payload examples), `PROJECT_CONTEXT.md` (deployment/DB context), `DEPLOYMENT_GUIDE.md`, and `REDISENO_2026-08.md` — the change log with the reasoning behind every non-obvious decision here; read it before undoing anything that looks odd. SQL lives in three files: **`RLS_MULTITENANT.sql`** is the current RLS state (applied and verified 2026-08-28), **`CHECKS_MACHINE_TANKS.sql`** holds the `machine_tanks` CHECK constraints that back the client-side price/min-level rules (applied 2026-08-28), while **`FIX_RLS_Y_PERFIL.sql`** is superseded history — re-running its PASO 2 would silently restore `using (true)` policies and undo the multi-tenant filter, since SELECT policies combine with OR. Consult these before making schema or architecture assumptions.
